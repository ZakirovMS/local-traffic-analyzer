# ПРАВИЛА РАБОТЫ ДЛЯ КОМАНДЫ

**Важно:** Мы работаем через форки. Создайте форк основного репозитория, ведите разработку в нем, а затем отправляйте Pull Request в основной репозиторий.

## Организация командной работы

Для организации работы команды используются **GitHub Issues**. Все задачи, обнаруженные ошибки и вопросы, требующие технического обсуждения, фиксируются в Issues репозитория.

### Типы Issues

Для создания Issue предусмотрены три шаблона:

| Шаблон | Назначение |
|---|---|
| **Задача (Task)** | Постановка конкретной задачи по разработке, настройке или улучшению проекта. |
| **Обсуждение (Discussion)** | Обсуждение архитектуры и согласование деталей реализации. |
| **Сообщение об ошибке (Bug Report)** | Описание обнаруженной ошибки с указанием условий её возникновения и ожидаемого поведения. |

При создании Issue необходимо выбрать подходящий шаблон и заполнить обязательные поля.

### Labels

Для классификации Issues используются следующие метки:

| Label | Назначение |
|---|---|
| `backend` | Go-сервисы |
| `frontend` | Frontend-разработка |
| `database` | Работа с базой данных|
| `devOps` | Docker, Docker Compose, CI/CD, Nginx и инфраструктура |
| `documentation` | Создание и обновление документации проекта |
| `other` | Задачи, не относящиеся к перечисленным категориям |

При создании Issue необходимо выбрать одну или несколько меток, соответствующих области проекта, к которой относится задача.

### Порядок работы

1. **Создание Issue.** Перед началом работы необходимо создать Issue с использованием подходящего шаблона.
2. **Назначение Labels.** Выбрать метки, соответствующие области проекта.
3. **Обсуждение.** Если для выполнения задачи требуется согласование технических деталей, обсуждение проводится в комментариях к Issue.
4. **Фиксация результата.** Принятые решения и результаты обсуждения необходимо зафиксировать в Issue.
5. **Завершение.** После выполнения задачи и проверки критериев приёмки Issue закрывается.

## Правила написания коммитов

Используем стандарт **Conventional Commits**.

**Формат:** `type(pkg): what was done` (с маленькой буквы, без точки в конце)

**Основные типы:**
* `feat:` — добавили новую фичу
* `fix:` — исправили баг
* `docs:` — поправили документацию
* `test:` — добавили или поправили тесты
* `chore:` — рутина, обновление зависимостей, настройка CI
* `refactor:` — переписали код, но логика не поменялась
* `build:` — изменения в системе сборки или зависимостях (Dockerfile, go.mod)
* `ci:` — изменения в конфигурации CI/CD (файлы workflow)
* `perf:` — изменения для улучшения производительности
* `style:` — исправление форматирования, пробелов и отступов
* `revert:` — откат предыдущего коммита

**В скобках:** указываем пакет, в котором были проведены изменения. Если изменения были в корне -
использовать ключевое слово `root`.

Примеры:
- `docs(frontend): change the description of the project structure`
- `build(root): add new dependence in go.mod`
- `feat(cmd/lta-analyzer): realisation of main logic`
